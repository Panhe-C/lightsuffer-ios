# PORTING.md — spektrafilm → Swift (slices 1, 2, 4, 5 and 6)

Status: **slice 1, 2, 4, 5 and 6 ported and validated** (2026-11-10).

This document is the map between the upstream Python engine
([spektrafilm](https://github.com/andreavolpato/spektrafilm) @ `3bb2c2d`, GPLv3)
and the pure-Swift `FilmPhysics` package of this repository.

* Upstream reference tree: `/workspace/spektrafilm/src/spektrafilm` (read only).
* Reference fixtures: `Tests/FilmPhysicsTests/Fixtures/slice1_*.json`,
  `slice2_*.json`, `slice4_catalog.json`, `slice5_spatial.json` and
  `slice6_stochastic.json`, generated by `tools/gen_fixtures.py` from the
  **unmodified** upstream engine.
* Bundled upstream data tables: `Sources/FilmPhysics/Resources/` (packed by
  `tools/pack_resources.py`, provenance in
  `Sources/FilmPhysics/Resources/CHANGELOG.txt`).
* The Swift port is a derivative work and is distributed under the GPLv3 as
  well (see `LICENSE`, `NOTICE`).

## 1. What the slices cover

### 1.1 Slice 1 — everything after `log_e_film`

The upstream topology has six taps:

```
rgb_in ──▶ log_e_film ──▶ cmy_film ──▶ log_e_print ──▶ cmy_print ──▶ rgb_out
```

Slice 1 ports everything **after** `log_e_film`:

| Stage | Upstream | Swift | State |
|---|---|---|---|
| spectral upsampling (camera) | `runtime/stages/filming.py` → `utils/spectral_upsampling.py` | — | **not ported** (the tap is injected) |
| negative development | `runtime/stages/filming.py::develop` → `model/develop.py::develop` | `Pipeline.swift::developFilm` | ported |
| DIR couplers | `model/couplers.py` | `Couplers.swift` | ported (per pixel, no diffusion) |
| printing (exposure) | `runtime/stages/printing.py::expose` | `Pipeline.swift::exposePrint`, `Printing.swift`, `Enlarger.swift` | ported |
| printing (development) | `runtime/stages/printing.py::develop` → `model/develop.py::develop_print_morph` | `Printing.swift::develop` | ported (morph inactive) |
| scanning | `runtime/stages/scanning.py::scan` | `Scanning.swift` | ported (no blur / unsharp / glare) |
| output gamut compression | `utils/gamut_compression.py::compress_rgb` | — | **not ported** (`"off"` in the slice 1 fixtures) |
| profile loading | `profiles/io.py` | `Profile.swift` | ported |
| parameter digest | `runtime/params_builder.py::digest_params` | `Digest.swift` | ported (film specifics) |

Public entry point:

```swift
let pipeline = try Slice1Pipeline(film: film, print: print, inputs: inputs)
let taps = try pipeline.run(logEFilm: image)   // -> cmyFilm, logEPrint, cmyPrint, rgbOut
```

### 1.3 Slice 4 — the whole catalogue, the digest and the direct scan

Slice 4 completes the engine: the **stock specific digest** of every stock,
the **direct scan** of a film (the path of the slides) and the **whole
catalogue** of the upstream engine — the 16 colour negatives printed on the 8
print media (128 looks) and the 20 films scanned directly (20 looks), i.e.
the **148 looks** of the upstream engine.

| Stage | Upstream | Swift | State |
|---|---|---|---|
| the stock specific digest | `runtime/params_builder.digest_params` | `Digest.swift` | ported (all three steps) |
| the neutral print filter database | `runtime/params_builder.apply_database_neutral_print_filters` | `NeutralPrintFilters.swift` | ported (per film / paper pair) |
| the film specifics (the DIR couplers) | `runtime/params_builder._apply_film_specifics` | `Digest.filmRender(for:base:)` | ported |
| the halation preset | `runtime/params_builder._apply_halation_preset` | `Digest.applyHalationPreset(_:)` | ported |
| the print specifics | `runtime/params_builder._apply_print_specifics` | `Digest.applyPrintSpecifics(_:)` | ported (a no-op upstream) |
| the direct film scan (`io.scan_film`) | `runtime/stages/scanning.py` | `Pipeline.swift::runScanFilm`, `Scanning.scan` | ported |
| the black / white reference of a scanned slide | `runtime/services/color_reference.py::_update_cmy_black_white_references` | `ColorReference.updateFilmReferences(film:cmyToLogXYZ:)` | ported |
| the catalogue (the stocks and the looks) | `model/stocks.py` | `StockCatalog.swift` | ported (28 stocks, 148 looks) |
| the hanatos 2025 tc LUT cache | `runtime/services/spectral_lut_compute.py::SpectralLUTService` | `HanatosTCLUTCache` | ported |

Public entry points:

```swift
// The parameters of a look, with the upstream defaults and the digest applied.
let params = try StockCatalog.pipelineParams(film: "kodak_portra_400")
let pipeline = try FilmPipeline(params: params)
let taps = try pipeline.process(rgbIn: image)

// The direct scan of a slide.
let params = try StockCatalog.pipelineParams(film: "fujifilm_velvia_100")
// -> params.io.scanFilm == true, the printing stage is skipped
```

The digest is **idempotent** and **non destructive**: a value that still
holds its upstream default is replaced by the stock specific one, a value the
user has customised is left alone. The upstream engine digests the
parameters once, when the stock is selected
(`spektrafilm_gui.state.digest_after_selection`), and the GUI then edits the
digested values; the Swift digest can therefore be applied every time a
pipeline is created without loosing the live parameters of the app.

## 1.4. Slice 5 — the deterministic spatial effects

Slice 5 ports the **deterministic** spatial effects of the upstream engine.
They live in the three stages of the pipeline and are applied in the order of
the upstream:

```
rgb_in ──▶ spectral upsampling ──▶ raw
                                   │
                                   ├─▶ boost_highlights        (the highlight boost)
                                   ├─▶ diffusion filter        (the camera)
                                   ├─▶ gaussian blur            (the lens of the camera)
                                   ├─▶ scatter + halation       (the negative)
                                   ▼
                                log_e_film ──▶ develop ──▶ cmy_film
                                                       │  (the DIR coupler diffusion)
                                                       ▼
                                            log_e_print ──▶ develop ──▶ cmy_print
                                                                        │
                                                                        ▼
                                                                 rgb_out
                                       (the diffusion filter of the enlarger, the lens
                                        blur and the unsharp mask of the scanner)
```

| Effect | Upstream | Swift | State |
|---|---|---|---|
| the separable Gaussian filter (the FIR and the Young & van Vliet IIR paths) | `utils/fast_gaussian_filter.py::fast_gaussian_filter` | `SpatialEffects.swift::gaussianFilter` | ported |
| the exponential filter (the Gaussian mixture surrogate of the 2D exponential PSF) | `utils/fast_gaussian_filter.py::fast_exponential_filter` | `SpatialEffects.swift::exponentialFilter` | ported |
| the unsharp mask of the scanner | `model/diffusion.py::apply_unsharp_mask` | `SpatialEffects.swift::unsharpMask` | ported |
| the highlight boost | `utils/numba_boost_hightlights.py::boost_highlights` | `Halation.swift::boostHighlights` | ported |
| the in emulsion scatter and the back reflection halation | `model/diffusion.py::apply_halation_um` | `Halation.swift::apply` | ported |
| the spatial diffusion of the DIR coupler inhibitors | `model/couplers.py::compute_exposure_correction_dir_couplers` | `Couplers.swift::exposureCorrection` | ported |
| the diffusion filters of the camera and of the enlarger (the four families) | `model/diffusion.py::apply_diffusion_filter_um` | `DiffusionFilter.swift::apply` | ported |
| the lens blur of the camera | `model/diffusion.py::apply_gaussian_blur_um` | `Filming.swift::expose` | ported |
| the lens blur of the scanner | `model/diffusion.py::apply_gaussian_blur` | `Scanning.swift::scan` | ported |
| the lens blur of the enlarger | — | — | **dead code upstream** (the upstream never reads `enlarger.lens_blur`) |
| the grain | `model/grain.py::apply_grain` | `Sources/FilmPhysics/Grain.swift` | **ported** (the slice 6, see §1.5) |
| the glare of the print | `model/glare.py::add_glare` | `Sources/FilmPhysics/Glare.swift` | **ported** (the slice 6, see §1.5) |
| the debug switches (`deactivate_spatial_effects`, `deactivate_stochastic_effects`, `lut_mode`) and the preview mode | `runtime/params_builder.py::digest_params` | — | **not ported** |

The pixel size of the negative — the scale of every micrometre effect — is
computed by the port exactly like the upstream:

```
pixel_size_um = film_format_mm * 1000 / max(height, width)
```

(`runtime/services/resize.py::ResizingService.crop_and_rescale`).

Public entry point (unchanged):

```swift
let pipeline = try FilmPipeline(params: params)
let taps = try pipeline.process(rgbIn: image)
// -> logEFilm, cmyFilm, logEPrint, cmyPrint, rgbOut
```

The spatial effects are *inside* the pipeline: the taps of a run with the
spatial effects on are the taps of the same run with them off, computed
through the spatial kernels.

## 1.5. Slice 6 — the stochastic effects (the grain and the glare)

Slice 6 ports the two **stochastic** effects of the upstream engine: the
grain of the negative and the veiling glare of the print.

Neither of them can be reproduced bit for bit:

* the upstream grain reseeds the **global legacy NumPy random state** with a
  fixed seed per channel and sub layer (`[0, 1, 2]`, `+ 10` per sub layer),
  so the upstream grain is deterministic but its stream is the legacy
  Mersenne Twister of NumPy,
* the upstream glare draws from the **unseeded** global NumPy random state,
  so the upstream glare is not reproducible at all.

The port therefore draws from its own generator — **xoshiro256\*\*** seeded
with **SplitMix64** — and makes the seed an **explicit parameter** of the
pipeline (`PipelineParams.stochastic.seed`), so that a render is exactly
reproducible on every platform (the whole arithmetic is defined on `UInt64`
with wrapping operators, so the same seed gives the same stream on Linux,
macOS and iOS).

| Effect | Upstream | Swift | State |
|---|---|---|---|
| the grain of the negative | `model/grain.py::apply_grain` → `apply_grain_to_density_layers` → `layer_particle_model` | `Sources/FilmPhysics/Grain.swift` → `Grain.apply(...)` | ported |
| the single layer model of the grain | `model/grain.py::apply_grain_to_density` | `Grain.apply(...)` (`sublayers_active = false`) | ported |
| the micro structure of the emulsion | `model/grain.py::add_micro_structure` | `Grain.addMicroStructure(...)` | ported |
| the interpolation of the emulsion layers | `model/density_curves.py::interp_density_cmy_layers` | `Grain.interpolateLayers(...)` | ported |
| the veiling glare of the print | `model/glare.py::add_glare` → `compute_random_glare_amount` | `Sources/FilmPhysics/Glare.swift` → `Glare.apply(...)` | ported |
| the random variates (the uniform, the normal, the Poisson, the binomial, the lognormal) | `utils/fast_stats.py` (the fast kernels) and the SciPy generators (the default path) | `Sources/FilmPhysics/Random.swift` → `RandomGenerator` | ported (the fast kernels, see §3.4) |
| the seed of the stochastic effects | the fixed seeds of the upstream / the unseeded global state | `Random.swift` → `StochasticSeed` | **the port makes the seed explicit** |

The glare is added to the **tristimulus values** of the scan, before the
conversion to RGB (upstream reference: `model/glare.py::add_glare`), and the
upstream does not apply any glare to a directly scanned film
(`io.scan_film`): the port reproduces both.

### The reference fixture

`Tests/FilmPhysicsTests/Fixtures/slice6_stochastic.json` holds, for the 16
cases of the slice (four stocks × four images):

* the parameters of the case (the digested upstream parameters),
* the statistics of the grain of **12 upstream realisations** and their
  aggregate, against the two upstream samplers (the exact SciPy generators
  and the fast kernels),
* the statistics of the glare of **12 upstream realisations** and their
  aggregate.

The upstream seeds are shifted by `1000 · (seed + 1)` to measure the spread
of the upstream; the algorithm of the upstream is not touched.  The grain is
only visible on a narrow film format (the amplitude of the shot noise scales
with one over the square root of the number of particles a pixel holds, i.e.
with the area of the pixel), so the cases use a 1 mm film format, i.e. a
pixel of 15.6 µm on the 64 × 64 images of the fixture.

The validation compares the **summary statistics** of the field of the
effect — the mean and the standard deviation of every channel, the
autocorrelation of the centred field at the lags 1, 2, 3, 5 and 8, the
correlation of the three channels and the quantiles 5 %, 25 %, 50 %, 75 %
and 95 % of the density histogram, i.e. 19 statistics per case — against the
aggregate of the upstream.  The gate of that comparison is described in
§3.4.

## 3. Numerical fidelity notes

### 3.1 Slice 1

The port follows the upstream code line by line. The points that needed care:

1. **`fast_interp` is not `numpy.interp`.** The upstream kernel
   (`utils/fast_interp.py`) uses a per channel axis
   (`log_exposure[:, None] / gamma_factor`), clamps the values outside the
   axis, is right biased on the axis knots and gives a zero slope to
   duplicated axis entries. `DensityCurves.interpolateExposureToDensity`
   reproduces all of it; `Numerics.interpolate` reproduces the plain
   `numpy.interp` used by the DIR coupler inversion (clamping, exact knot
   values, `NaN` in → `NaN` out).
2. **`numpy.interp` on a non monotonic axis.** The DIR coupler inversion
   interpolates on `log_exposure - inhibitors`, which is ascending for every
   shipped profile (verified for Portra 400 in `ProfileLoaderTests`). The
   Swift implementation follows the `numpy.interp` semantics for an
   ascending axis.
3. **The normal CDF.** `scipy.stats.norm.cdf` is reproduced with
   `erf`/`erfc` built on the regularised incomplete gamma function
   (series + continued fraction). The agreement with SciPy is ≤ 1e-14
   (`NumericsTests.testNormalCDF`).
4. **`NaN` handling.** The upstream profiles store the missing measurements as
   `NaN` (JSON `null`); the Swift loader maps `null` to `Double.nan`.
   `density_to_light` turns a `NaN` density into *no* light, `nan_to_num`
   turns the `NaN` sensitivities into zero — both reproduced.
5. **The XYZ → RGB matrix of the scanning stage.** `colour.XYZ_to_RGB`
   applies the CAT02 adaptation **to the input** and then the (unadapted)
   sRGB matrix. The reference fixture stores the resulting matrix the way
   `colour.XYZ_to_RGB(identity, …)` returns it, i.e. **row `i` is the RGB
   response to the `i`-th XYZ basis vector**; the port therefore converts
   with the row vector product `rgb = xyz · matrix`. (The note of the fixture
   calls it `rgb = result @ xyz`, which is the transposed convention — the
   *data* is right, the wording of the note is not.)
   The sRGB → sRGB matrix of the output transfer function is applied the
   other way round (`rgb = matrix · rgb`), exactly like
   `colour.RGB_to_RGB`.
6. **The sRGB matrices** are the rounded ones of `colour-science`
   (`3.2406, -1.5372, …`), so that the Lab conversion of the port agrees
   with the upstream engine to the last digits.
7. **The print development uses the fitted CDF model**
   (`utils/morph_curves._evaluate_fitted_density`), not the stored density
   curves — the stored curves are only used by the black/white reference of
   the print, exactly as upstream.

### 3.2 Slice 2

1. **The hanatos 2025 lookup table.** The upstream builds a 192 × 192 × 3
   table over the chromaticity (`tc.x`, `tc.y`) of the scene: the spectrum of
   the table (`irradiance_xy_tc.npy`, float16) is weighted by the log
   sensitivity of the film and by the normalised band pass window of the
   adaptation. The port rebuilds the table from the same three ingredients
   (the bundled float16 spectrum, the profile sensitivity and the window of
   the profile) — the measured agreement is **2.4e-7 relative**.
2. **The lookup is a Mitchell–Netravali cubic** (`B = C = 1/3`) on a
   *reflected* border (`SpectralUpsampling.lookup`), not a bilinear
   interpolation.
3. **The input gamut compression is baked into the table**, the way the
   upstream does it (`remap_tc_lut_for_compression`):
   `new_lut[xy] = old_lut[compress(xy)]`. The compression itself is a radial
   Reinhard knee against the polygon of the spectral locus
   (`compress_xy_radial`).
4. **The chromatic adaptation is computed, not loaded.** The filming stage
   adapts the ProPhoto primaries to the reference illuminant of the film
   (D55) with **CAT16** (the upstream `_rgb_to_tc_b` calls
   `colour.RGB_to_XYZ(..., chromatic_adaptation_transform="CAT16")`); the
   scanning stage adapts the scan illuminant to the sRGB white point with
   **CAT02** (the default of `colour.XYZ_to_RGB`); the sRGB → sRGB matrix of
   the output transfer function is the **CAT02** round trip of
   `colour.matrix_RGB_to_RGB(sRGB, sRGB)` (its default transform; the
   reference fixture stores the `1.182393e-16` entry of that very matrix).
5. **The bundled spectral tables are `float32`.** The illuminant spectra and
   the CMFs are narrowed from double to float32 when they are packed (the
   hanatos irradiance table keeps its upstream float16 payload verbatim).
   That costs ≈ 1e-7 relative on the chromaticity of the reference
   illuminant, which is the floor of the colour matrix parity: the `Z` row
   of the ProPhoto matrix is a *difference of larger terms*, so its relative
   error reaches 1.3e-6 while its absolute error stays at 1.9e-9.
6. **The CAM16-UCS output compressor** builds its own table of the maximum
   in-gamut chroma (64 lightness samples × 720 hues, 18 bisection steps, the
   same `numpy.linspace` grids as the upstream) and compresses the chroma
   with a Reinhard knee; the lightness is compressed one-sided with the
   white point of the output colourspace as the reference.
7. **The print balance reference is computed by the port.** The 0.184 grey
   patch is upsampled in **sRGB without CCTF decoding** (the default of the
   upstream helper), whatever the input colourspace of the pipeline is, and
   developed with the *un-normalised* density curves of the film — the
   upstream subtlety reproduced in `Filming.densitySpectralMidgray`.

### 3.3 Slice 5

The spatial effects are the part of the upstream with the sharpest edges:
the port had to reproduce four conventions exactly.

1. **Two different reflections.** The upstream uses *two* reflection
   conventions and they are **not** the same:
   * the FIR Gaussian filter uses `scipy.ndimage`'s `reflect` mode, i.e. the
     edge sample **is** repeated (`d c b a | a b c d | d c b a`); the port
     reproduces the `_reflect` helper of the upstream
     (`SpatialEffects.reflectIndex`),
   * the diffusion filter pads its image with `numpy.pad(..., mode="reflect")`,
     i.e. the half sample symmetric reflection **without** the repeated edge
     sample (`d c b a | a b c d | d c b a` with `d` next to `a`); the port
     reproduces it with `DiffusionFilter.numpyReflectIndex`.

   Mixing the two up shifts the diffusion filter by one pixel at the borders
   (measured: a max abs error of 0.006 on the log exposure of the negative).
2. **The Gaussian filter dispatches on the sigma.** Below three pixels the
   upstream uses a fused separable FIR (the vertical pass first, then the
   horizontal one, the sums accumulated in the order of the kernel), above
   it a recursive Young & van Vliet IIR (a forward and a backward sweep, the
   boundary handled by the sample replication). The port implements both
   paths, with the same summation order, so the results agree to the last
   bits (measured: a max abs error of 6e-8, i.e. the rounding of the
   fixtures).
3. **The exponential filter is a Gaussian mixture with a fixed fit.** The
   upstream approximates the isotropic 2D exponential PSF with three
   Gaussians of fixed amplitude and sigma-to-decay ratio
   (`0.1633 / 0.5360`, `0.6496 / 1.5236`, `0.1870 / 2.7684`). The amplitudes
   sum to **0.9999**, not to one: the filter is therefore *not* exactly
   energy preserving and the port reproduces the constant verbatim.
4. **The convolution of the diffusion filter is an FFT convolution.** The
   upstream pads the image (a `numpy` `reflect` pad of the radius of the
   kernel), convolves it with `scipy.signal.fftconvolve(..., mode="same")`
   and crops the result back to the size of the image. The port evaluates the
   same *linear* convolution directly (the kernel is at most 31 × 31), which
   agrees with the FFT to the round off of the transform (measured: 3e-15).

Two upstream details are **dead code** and are documented rather than ported:
the lens blur of the enlarger (`enlarger.lens_blur` is never read by the
upstream pipeline) and the glare of the negative (`film_render.glare` is
never read either; only `print_render.glare` is).

The **stochastic** effects are ported in the slice 6 (§1.5): the grain draws
its particles from the Poisson and binomial variates of the port (the fixed
seeds `[0, 1, 2]` of the upstream become an explicit seed of the pipeline)
and the glare of the print draws a lognormal from the seeded generator of
the port (the upstream draws it from the *unseeded* NumPy random state — the
upstream itself is not reproducible there).

### 3.4 Slice 6 — the statistical gate

The two stochastic effects cannot be compared tap by tap, so the validation
compares the **summary statistics** of the field of the effect (19 statistics
per case, see §1.5) with the aggregate of the upstream.  The gate of that
comparison is the point of this section: it must be wide enough not to fire
spuriously and **tight enough not to hide a deviation**.

#### The statistic

The comparison is a comparison of **means**:

* the upstream mean `μ` and the upstream spread `σ` are the aggregate of the
  `n = 12` upstream realisations of the fixture,
* the port value is the mean of `m = 12` independent realisations of the
  port (the port is deterministic for a given seed, so the realisations are
  independent draws of the same distribution).

Under the null hypothesis (the port and the upstream draw the same
distribution) the difference of the two means is `N(0, σ² · (1/m + 1/n))`,
so the standardised difference is

```
z = |port − μ| / (σ · sqrt(1/m + 1/n))
```

and, because `σ` is itself estimated from the `n` upstream realisations,
`z` follows a **Student t with `n − 1 = 11` degrees of freedom** under the
null.  (The port averages `m` realisations, so the variance of the
difference is `σ²(1/m + 1/n)` and not `σ²(1 + 1/n)`: the form of the review,
which treats the Swift value as one more independent draw, would inflate the
gate by a factor `sqrt(m) = 3.46`.)

#### The critical value `k`

The gate is `|z| ≤ k`, with `k` the quantile of that Student t
distribution at the level `1 − α / (2 · comparisons)`, `α = 1 %` the
family-wise false alarm rate and `comparisons = 836` the number of
comparisons of the family (the grain of the 16 cases against the two
upstream references — 608 — and the glare of the 12 applicable cases —
228):

```
k = t₁₁(1 − 0.01 / (2 · 836)) · sqrt(n / (n − 1))
  = 7.5026 · 1.0445 = 7.8362
```

The correction `sqrt(n / (n − 1))` accounts for the fact that the fixture
stores the *population* standard deviation of the upstream realisations
(the `ddof = 0` convention of NumPy) while the Student t distribution is
calibrated with the unbiased one (`ddof = 1`).

The Bonferroni correction is used and not the Šidák one: the statistics of a
case are strongly correlated (the mean, the standard deviation and the
quantiles of the same field) and the Šidák correction assumes independent
tests.  The **Student t** quantile is used and not the normal one: with the
normal quantile (4.3783) the per comparison false alarm rate would be
8.7e-4 instead of 1.2e-5, i.e. the family-wise rate would be of the order of
50 % and the test would fail at random about one run out of two.  The price
of that honesty is the width of the gate: `k · sqrt(1/m + 1/n) = 3.20 σ_up`,
i.e. a deviation of the port has to reach 3.2 standard deviations of the
upstream to be detected.  The fixture holds only 12 upstream realisations,
so the spread of the upstream is itself known to ±21 %; more upstream seeds
would tighten the gate (the quantile tends to 4.38 as the degrees of freedom
grow).

#### No relative and no absolute tolerance

The tolerance is `k · σ_up · sqrt(1/m + 1/n)`, i.e. it is entirely
determined by the measured spread of the upstream.  The gate of the first
revision of this slice was `max(4 σ, 5 % of the mean, 0.01)`: in 259 of the
836 statistics the 5 % floor was wider than 3 σ (for the `acf_1` of
`portra_400__flat_ev_minus2`, for instance, the spread of the upstream is
0.0034 and the floor 0.0258, i.e. 7.6 σ), so the gate hid the deviations it
was supposed to measure.  The new gate is 3.20 σ for the 809 statistics the
upstream resolves, and the resolution of the fixture for the 27 others; it
is **tighter** than the old one everywhere.

The single exception is a statistic whose upstream spread is **below the
resolution of the fixture** (the fixtures store seven significant digits):
such a statistic carries no information — its spread is then the floating
point noise of the upstream computation and not the spread of the statistic
— and the comparison falls back to the resolution of the stored values (half
of the last significant digit).  27 of the 228 statistics of the glare are
in that case (the correlation of the three channels of a flat case: the
glare is a single scalar field, so the correlation is exactly one and the
spread of the upstream is 1e-10).

#### The two references of the grain

The upstream draws the particles of the grain from the SciPy `poisson` and
`binom` generators (the default path) or from the kernels of
`spektrafilm.utils.fast_stats` (the `settings.use_fast_stats = True` path,
which replace the exact generators by normal approximations).  **The port
reproduces the fast kernels**, so the fixture measures both paths and the
validation compares the port with both:

* against the **fast** path (the same algorithm), the tolerance is the
  plain statistical gate: this is the *algorithm* gate of the port, and **no
  exception is allowed there**;
* against the **default** path (the exact generators), the port deviates by
  the approximation error of the samplers, which the fixture **measures
  explicitly** (the difference between the two aggregates of every case);
  that difference is added to the tolerance **in quadrature**
  (`sqrt((k σ)² + Δ²)`), it is not a maximum.

## 7. The Metal port (the GPU)

Status: **phase 1 implemented, validated on Linux against the CPU
reference; nothing is validated on a Metal device yet** (the CI of the
project is the first place where the Metal code runs, §7.8).

### 7.1 The architecture

The GPU port lives in the `FilmPhysicsMetal` target.  It is a **port of the
same chain**, not a different engine: the CPU reference (`FilmPhysics`)
stays the reference implementation and every number of the port comes from
the same precomputed data.

```
                 FilmRenderPlan  (pure Swift, FilmPhysics)
                          │  the precomputed data of a render
                          │  (Float32: the payload of the GPU buffers)
                          ▼
   rgb_in ──▶ raw ──▶ log_e_film ──▶ cmy_film ──▶ log_e_print ──▶ cmy_print ──▶ rgb_out
             │            │             │             │              │             │
       filmSpectral…   filmLinear…   filmFilm…    filmPrinting…   filmPrint…   filmXYZToRGB
       filmBoost…      filmCoupler…  filmGrain…   (the spatial     filmScanXYZ  filmGamutCompress
       (the filters)  filmFilm…      (the grain)  effects)                     filmEncodeOutput
```

| Piece | Where | Role |
|---|---|---|
| `FilmRenderBackend` | `Sources/FilmPhysics/FilmRenderBackend.swift` | the protocol of a renderer; `CPUBackend` is the reference implementation |
| `FilmRenderPlan` | `Sources/FilmPhysics/FilmRenderPlan.swift` | the precomputed data of a render (the tc LUT, the colour matrices, the characteristic curves, the DIR couplers, the spectral tables, the exposure factors, the gamut compression table) |
| `FilmPlanEvaluator` | `Sources/FilmPhysics/FilmPlanEvaluator.swift` | the pure Swift evaluation of the plan (in `Double`) |
| `FilmPlanEvaluatorFloat32` | `Sources/FilmPhysics/FilmPlanEvaluatorFloat32.swift` | the **executable specification** of the Metal kernels (in `Float32`) |
| `FilmGrainPlan` / `FilmCounterRandom` | `Sources/FilmPhysics/FilmGrainPlan.swift`, `FilmCounterRandom.swift` | the plan of the grain and the counter based generator (the reference of the GPU path) |
| `MetalBackend` | `Sources/FilmPhysicsMetal/MetalBackend.swift` | the GPU implementation of the protocol |
| `MetalPlan` | `Sources/FilmPhysicsMetal/MetalPlan.swift` | the structures the shaders read and the builders of the convolution kernels |
| `FilmShaders.metal` | `Sources/FilmPhysicsMetal/Shaders/FilmShaders.metal` | the 28 compute kernels |

The Metal Shading Language source is **compiled at runtime**
(`device.makeLibrary(source:options:)`): the package does not rely on
SwiftPM compiling the `.metal` files, and the source is shipped as a
resource of the target.

The **order** of the passes is the order of the CPU pipeline:

```
raw = 2^EV · upsample(rgb_in)
raw = boost(raw)                       filmBoostHighlights
raw = diffusion_filter(raw)            filmDiffusionFilter
raw = blur(raw, σ = lens blur)         filmBlurHorizontal / filmBlurVertical
raw = halation(raw)                    filmScatterCombine / filmHalationCombine
log_e_film = log10(raw · b/w + 1e-10)  filmLinearToLog
cmy_film = curves(log_e_film)          filmFilmDensity
cmy_film = couplers(cmy_film)          filmCouplerCorrection / filmFilmDensityCoupled
cmy_film = grain(cmy_film)              filmGrainLayers / … / filmGrainFinalize
log_e_print = log10(print_exposure)    filmPrintingExposure / filmLinearToLog
cmy_print = curves(log_e_print)        filmPrintDensity
xyz = scan(cmy_print)                  filmScanXYZ (+ the glare)
rgb = gamut_compress(xyz)              filmXYZToRGB / filmGamutCompress
rgb = encode(rgb)                      filmEncodeOutput
```

### 7.3 The `Float32` notes

* The plan stores **every** number in `Float32`: it is the payload of the
  GPU buffers, so the pure Swift plan evaluator and the Metal kernels see
  exactly the same numbers.  The `Float32` epsilon is `2⁻²⁴` ≈ 6e-8
  (relative).
* The **arithmetic** of the GPU path is `Float32` from end to end: the
  spectral upsampling, the interpolation of the curves, the spectral
  integrals, the CAM16 model and the output transfer function.
* The *conditioning* of the chain is what turns the `Float32` epsilon into
  the measured error:
  * the **cubic** lookup of the hanatos 2025 table is sensitive to the
    position (its derivative is of the order of 1.5 per cell of the 192 ×
    192 table) and the weights of the cubic kernel cancel each other: a
    relative error of 6e-8 on the chromaticity is amplified by about
    thirty,
  * the CAM16 round trip of the output gamut compression divides by
    quantities of the order of 0.1: the amplification is of the order of a
    thousand.
* The measured errors (the `Float32` plan evaluator against the CPU
  pipeline, §7.5): the intermediate taps are within **5.3e-6**, the output
  is within **2.2e-4** (a mean ΔE₀₀ of 0.0046 and a max ΔE₀₀ of 0.0107).
* The plan evaluator in `Double` is three orders of magnitude better (the
  taps within 2.8e-7, the output within 3e-6 of ΔE₀₀): the plan itself is
  *not* the source of the error of the GPU, the `Float32` arithmetic is.

### 7.4 The tolerances and their justification

The tolerances of the Linux validation (`FilmPlanEvaluatorTests`) are
**derived from the measured errors**, not chosen:

| Quantity | Measured maximum | Tolerance | Justification |
|---|---|---|---|
| the intermediate taps (`log_e_film`, `cmy_film`, `log_e_print`, `cmy_print`) | 5.3e-6 | **1e-5** | the measured maximum times 1.9; the headroom covers the profiles that are not in the fixtures (a steeper curve) |
| the mean ΔE₀₀ of the output | 0.0046 | **0.008** | the measured maximum times 1.7 |
| the max ΔE₀₀ of the output | 0.0107 | **0.021** | the measured maximum times 2.0 |

The **headroom is at most a factor of two** of the measured maximum, and
the measured maximum is itself the `Float32` epsilon times the measured
conditioning of the chain (§7.3): the tolerance is not a "loose floor" but
a bound on the rounding of the GPU arithmetic.

The tolerance of the Metal tests (the macOS CI) is the acceptance criterion
of the plan (a mean ΔE₀₀ below 0.5) plus the comparison of the GPU with
the executable specification of the kernels (a max abs error below 1e-3 on
the encoded output, i.e. about four times the measured error of the
`Float32` evaluator).

### 7.6 The RNG design (the grain and the glare)

The GPU has **no order**: the pixels are processed in parallel.  A
sequential generator (the xoshiro256\*\* of the CPU reference) cannot be
used, because the value of a variate would depend on the order of the
pixels.

The GPU port therefore uses a **counter based** generator
(`FilmCounterRandom`, transliterated into the shading language as
`filmHash32` / `filmCounter` / `filmUniform`):

* the variate of a pixel is a pure function of
  `(seed, pixel, layer, channel, stream)`,
* the hash is the 32 bit avalanche finaliser of Chris Wellons
  (`lowbias32`), mixed with the odd constants of the golden ratio,
* the uniforms use the 24 high bits of the hash (the resolution of a
  `float` mantissa),
* the normal variate is the Box-Muller transform of two uniforms (it needs
  exactly two, which is what a counter based generator can afford).

The **distributions** are the ones of the upstream fast kernels (the ones
the CPU reference reproduces): the Poisson variate is Knuth's product method
below a mean of thirty and a normal approximation above it, the binomial
variate is a direct simulation below twenty five trials, a normal
approximation when the variance is above ten and the inversion of the
cumulative distribution otherwise.  The realisation differs (a different
source of randomness), the distribution does not.

The consequence is that the grain of the GPU is **not** bit identical with
the grain of the CPU: it is validated **statistically**, with the gate of
§3.4:

* the pure Swift reference of the GPU path (`FilmGrainPlan.apply`) is
  compared with the grain of the CPU reference over the 16 cases of the
  slice 6: the worst z-score is **4.37** (the gate is `k` = 7.90 for the
  1140 comparisons of the family),
* the same reference is compared with the **upstream**: the only statistics
  above the statistical gate are the four that the model difference of the
  samplers explains (§3.4), and they are covered by the measured sampler
  difference (added in quadrature, exactly like the existing grain
  validation does).

The number of realisations of that comparison is six (the upstream averages
twelve): the tolerance of the gate accounts for it
(`k · σ · sqrt(1/m + 1/m)`), so the comparison stays honest.

### 7.7 What is validated on Linux and what only on macOS

| Validated on Linux (the CI of the repository, no GPU needed) | Validated only on macOS (the Metal CI job) |
|---|---|
| the plan reproduces the CPU pipeline tap by tap (`FilmPlanEvaluatorTests`) | the Metal kernels against the CPU pipeline (a mean ΔE₀₀ below 0.5) |
| the `Float32` specification of the kernels against the CPU pipeline | the Metal kernels against the `Float32` specification (a max abs error below 1e-3) |
| the static analysis of the shading language: the kernel names are unique, every dispatched kernel exists, the buffer indices are contiguous, the structures have the layout of their Swift counterparts, there is no `double` (`MetalSourceTests`) | the spatial effects on the GPU (the halation, the diffusion filters, the lens blurs, the unsharp mask) |
| the counter based grain against the grain of the CPU and against the upstream (`GrainCounterTests`) | the grain of the GPU against the grain of the CPU (the statistical gate) |
| the compilation of the package and of the test targets on Linux | the timing of the GPU against the CPU (a 1024 × 1024 image, the median of three runs after a warm up) — note that the CPU side of that measurement costs about **85 s per run** in a debug build (the release build is about twenty times faster) |

**Nothing on Metal is validated until the CI runs it on a real Metal
device**: the MSL source, the Swift/Metal API calls and the buffer layouts
are written to be correct, and the *logic* of the kernels is validated on
Linux through the executable specification, but the code itself has never
been compiled by a Metal compiler.

### 7.8 The CI

`.github/workflows/ci.yml` runs, on `macos-15` (a timeout of 40 minutes):

1. the checkout, `swift --version` and `xcrun --show-sdk-path`,
2. the Metal devices of the machine (`system_profiler SPDisplaysDataType`),
3. `swift build`,
4. `swift test 2>&1 | tee test.log` (the log is uploaded as an artifact),
5. `xcodebuild -list` and the build of the package scheme for the iOS
   Simulator (`-destination 'generic/platform=iOS Simulator'`), the scheme
   being detected in the script.

The tests print their measurements with the prefixes `METAL-PARITY` and
`METAL-TIMING`, so that the log of the job can be grepped.

### 7.9 The deferred items

* the **single layer model** of the grain (`grain.sublayers_active = false`)
  is not ported to the GPU: the backend raises
  `MetalBackendError.invalidPlan` for it (the upstream default is the sub
  layer model),
* the **Young & van Vliet IIR** Gaussian of the CPU is replaced by the FIR
  kernel on the GPU (the truncation at three sigmas): the difference is a
  few ulps on a blurred field, it is *not* measured yet,
* the **auto exposure**, the **lut modes** and the **debug switches** of
  the upstream are not ported (they are not ported on the CPU either),
* the **input gamut compression** is baked into the tc lookup table (as it
  is on the CPU), it is not a GPU pass,
* the **Metal performance** of the grain is not measured: the inversion of
  the cumulative distribution of the binomial is a loop of up to `n`
  iterations for the high exposure cases (the same loop as the CPU
  reference).
